What is conjoint analysis?

Conjoint analysis is a quantitative method for measuring how people make trade-offs. Participants are shown pairs (or small sets) of alternatives that differ systematically across several attributes—for example, price, quality, and brand—and asked to choose the one they prefer. By repeating this across many tasks, the method recovers the weight each person places on each attribute level, even when they cannot articulate those weights directly.

The method is widely used in political science, health research, and environmental policy, and is gaining traction in human-computer interaction for studying preferences around privacy and data use in smart systems or consumer technology features.

This tool simplifies setup and administration, allowing participants to evaluate alternatives embedded in AI-generated textual or visual scenarios, more closely reflecting actual decision-making.

What the platform does

The platform covers the full research lifecycle—from designing your study and generating stimuli, to collecting responses and exporting analysis-ready data --- through a browser-based interface that requires no programming.

🎛️

Guided study setup

A step-by-step wizard walks you through survey title, attributes and levels, presentation mode, and participant introduction. AI-assisted attribute suggestions can accelerate brainstorming, though final design decisions remain yours to make. The conjoint design is generated on demand from the survey page, where a warning highlights when regeneration is needed after configuration changes.

📐

Statistically sound designs

The platform generates D-efficient conjoint designs using a coordinate exchange algorithm with multiple random restarts. Blocked designs are supported for large profiles, and a built-in sample size estimator provides real-time guidance.

🤖

AI-generated stimuli

Beyond standard tables, the platform can generate a short scenario text or a synthetic image for every profile in your design, using your prompt as a template and appending the attribute-level details automatically.

🔗

External survey integration

Participants arrive via a redirect from your existing survey platform (Qualtrics, SoSci Survey, LimeSurvey, etc.) carrying a unique participant key. After completing the conjoint tasks they are redirected back, closing the loop.

📦

Research-data-management export

A single ZIP archive contains long-format response data with a data dictionary, the full design matrix, generated stimuli with their prompts, a design.yaml study-configuration record, and an R starter script ready for conditional logit estimation.

📊

Live results view

A results page shows preliminary part-worth utilities and relative attribute importance as data accumulate. A shareable, token-authenticated link lets collaborators or project stakeholders view results without accessing the full survey configuration.

🔓

Free and self-hosted

No subscription, no per-response fees. You host the application on your own infrastructure; participant data never leaves your server. The only optional external service is an OpenAI API key for AI-generated stimuli.

👥

Collaboration and access control

Researchers log in via their ORCID iD. Surveys can be shared between ORCID accounts with owner or collaborator roles, making the platform suitable for multi-researcher projects.

Three stimuli presentation modes

All three modes share the same underlying conjoint design and response collection logic. The choice of mode affects how each alternative is presented to participants.

📋 Tabular

The standard conjoint format: a table with attribute rows and alternatives as columns.

  • Maximum comparability
  • No API key required
  • Well-tested in the literature
📝 Textual (AI scenario)

Each alternative is shown as a short AI-written scenario that embeds the profile in natural language.

  • Supports holistic evaluation
  • Useful for complex social or product scenarios
  • Requires an OpenAI API key
🖼️ Visual (AI image)

Each alternative is shown as an AI-generated image produced from the researcher's base prompt and profile details.

  • High ecological validity for product or design research
  • Supports low / medium / high generation quality
  • Requires an OpenAI API key

Note on AI stimuli and research integrity. AI-generated stimuli are produced from researcher-specified profiles and prompts. The design structure—attributes, levels, and framing—remains entirely the researcher's theoretical decision and must be grounded in prior literature. Generated stimuli should be reviewed before field deployment; the platform supports individual regeneration so that problematic outputs can be replaced without rerunning the entire batch.

How a study works

1

Configure your survey

Use the setup wizard to define your research context, attributes and levels, presentation mode, and participant introduction text. A warning on the survey page highlights whenever the conjoint design needs to be (re-)generated after configuration changes.

2

Generate the design and stimuli

Click Generate Design on the survey page to produce a D-efficient conjoint design. For textual or visual surveys, write a base prompt and trigger AI generation from the Inspect Design page—one stimulus at a time to test your prompt, then the full batch. Any individual result can be regenerated without rerunning the whole batch.

3

Embed in your existing survey

Copy the entry URL into your Qualtrics, SoSci Survey, or LimeSurvey flow as a redirect, passing the participant key as a URL parameter. The platform handles all conjoint task sequencing and response storage.

4

Collect and export

Monitor completion rates on the survey detail page. Download the export bundle at any time: a long-format response CSV, the design matrix, all stimuli with prompts, a design.yaml configuration record, and an R analysis starter script.

Hosting requirements

The platform is a self-contained Python web application. No separate database server, message broker, or build pipeline is required. A modest virtual server or research computing allocation is sufficient for most studies.

Server Any Linux VPS or cloud instance (1 vCPU, 512 MB RAM is enough for typical research loads). The application can also run on institutional HPC login nodes or department servers.
Python Python 3.10 or later. All dependencies are listed in requirements.txt and installable with pip. A virtual environment (venv) is recommended.
Database SQLite by default—no separate database process needed. The entire dataset is a single file, easy to back up and archive. PostgreSQL or MySQL can be configured for high-concurrency deployments.
WSGI server Gunicorn or uWSGI behind a reverse proxy (nginx or Apache) for production. For small studies in secure environments, Flask's built-in server can be used directly.
ORCID OAuth A free ORCID public API credential (client ID and secret) is required for researcher authentication. Obviously, participants do not require ORCIDs.
OpenAI API key (optional) Required only for textual or visual stimuli generation. Standard API pay-per-use pricing applies. Conventional tabular conjoint surveys work with no external API dependency.

Quick start

# 1. Clone the repository
git clone https://github.com/[REPO].git
cd conjoint

# 2. Create a virtual environment and install dependencies
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# 3. Set environment variables (see config.py for the full list)
export SECRET_KEY="your-secret-key"
export ORCID_CLIENT_ID="your-orcid-client-id"
export ORCID_CLIENT_SECRET="your-orcid-client-secret"
export OPENAI_API_KEY="sk-..."   # optional, for AI generated stimuli

# 4. Run the application
flask run

Full deployment instructions, including nginx configuration and systemd service setup, are available in the repository's README.md.
